# 設計メモ

## 1. 全体構成

- Windows 向けデスクトップアプリ（Electron）。各PCのアプリが、社内の共有フォルダのファイルを直接読み書きする。サーバー・ポート・ログインは使わない。
- 画面（`public/`、素の TypeScript）と処理（`src/server/`）は、アプリ独自のプロトコル `app://meishi/` でつなぐ（`src/desktop/main.ts`）。ネットワークのポートは開かない。
- 利用者は Windows ユーザー。アクセスできる人は共有フォルダの権限で決まる。表示名は共有フォルダの `users/<ユーザーID>.json`（各PCが自分のファイルだけを書く）。
- 設定は各PC・各利用者の `%APPDATA%\MeishiKanri\settings.json`。全員の初期値は exe と同じフォルダの `meishi-config.json`（任意）。

## 2. 保存方式：共有フォルダ上の SQLite を採用しない理由

SQLite 公式資料は次の趣旨を述べている（下記 URL。**この開発環境からは sqlite.org に接続できず本文を再取得できなかったため、原文は社内で確認してください**）。

- <https://www.sqlite.org/useovernet.html>：ネットワークファイルシステムのファイルロックや書き込みの同期は不完全なことがあり、破損の原因になり得る。複数のPCから同じDBファイルを開く使い方は推奨されない。
- <https://www.sqlite.org/wal.html>：WAL モードはネットワークファイルシステム上では動作しない。
- <https://www.sqlite.org/howtocorrupt.html>：ロック実装が壊れている／欠けているファイルシステムが破損原因として挙げられている。

今回は「複数のPCが同じ共有フォルダを直接使う」構成なので、DBファイル1つを共有する方式はなおさら避けた。代わりに、**1名刺＝1ファイルで、ファイル単位にアトミックに更新するストア**を使う（`src/server/store.ts`）。

## 3. ファイルストア

```
<保存先>\
  .meishi-store        目印（初期化時に作成。無ければ一切書き込まない）
  .changed             書き込みのたびに更新（他のPCの変更検知用）
  cards\<id>.json      名刺1件 = 1ファイル（version 付き）
  images\<id>.jpg      画像（不変。差し替え時は新しい ID）
  trash\<id>-<時刻>.json  削除した名刺
  locks\<名前>.lock    PC間のロック
  users\<ユーザー>.json  表示名
  inbox-done\          取り込み済みの元ファイル（保持期間後に削除）
  backups\meishi-YYYYMMDD-HHMMSS-<auto|manual|pre-restore>.tar
```

| 脅威 | 対策 |
|---|---|
| 書き込み途中の異常終了・通信断 | 一時ファイルに書いて `fsync` → 同じフォルダ内で `rename`（置き換え）→ 読み戻して内容一致を確認。旧版か新版のどちらかが必ず残る |
| 複数PCの同時更新 | 名刺ごとのロックファイル（排他作成 `wx`）。ロックの中でディスク上の最新版を読み、`version` が違えば 409（競合）。画面に差分を表示し、上書きするかは本人が選ぶ |
| ロックを持ったままPCが停止 | 保持中は10秒ごとにロックの更新日時を更新。30秒更新が無いロックは放棄扱い |
| 他のPCの変更の反映 | 一覧のたびに `.changed` を読み、変わっていれば更新日時・サイズが変わったファイルだけ読み直す（60秒ごとに全件確認も行う）。詳細・編集画面は常にディスクから最新を読む |
| 名刺と画像の不整合 | 画像を先に保存し、名刺保存時に参照画像の存在を確認。参照されない画像は24時間後に掃除（`jobs` ロック） |
| 共有フォルダ切断 | 書き込み前に目印を確認。失敗時は明確なエラーを返し、別の場所へ保存しない。入力内容は画面に残る |
| 読み込めないファイル | 削除せずに残し、一覧から除外してログに記録 |
| バックアップの整合 | `jobs` ロック中（画像の掃除と排他）に最新の名刺を読み、参照画像とともに tar に書き出す。`manifest.json` に全ファイルの SHA-256。書き出し後に検証してから正式名に rename。自動バックアップはどのPCが実行してもよく、ロックで1台に限られる |
| 復元 | `maintenance` ロック（他PCの保存を「復元作業中」として拒否）→ 書き込み中のロックが消えるのを待つ → 検証 → 現データを `pre-restore` に退避 → staging に展開 → マーカーを書いてから `cards`/`images` を入れ替え。途中で止まっても次回起動時（どのPCでも）に完了させる |

読み込みはメモリ上の索引で行う。数千件程度を想定。

### SMB 運用上の注意（社内環境で要確認）

- 一般的な Windows ファイルサーバー／NAS（Samba）では、同一フォルダ内の置き換え rename はアトミックに扱われるが、機種・設定（キャッシュ、ウイルス対策のリアルタイム検査）によっては一時的に失敗することがある。その場合は保存失敗として表示されるので、もう一度保存する。
- ロックの「30秒」は各PCの時計ではなく、共有フォルダ上のファイルの更新日時で判断する。ファイルサーバーと各PCの時計が大きくずれていると誤判定し得るため、社内の時刻同期が前提。

## 4. セキュリティ

- 外部通信なし：画面は CSP `default-src 'self'`。加えて main プロセスで `app:` `blob:` `data:` 以外のリクエストを遮断。外部リンク（Web・メール・電話）は既定のアプリで開き、アプリ内では表示しない。カメラ等の権限要求はすべて拒否。
- Electron：`contextIsolation`・`sandbox` 有効、`nodeIntegration` 無効、preload なし。単一インスタンス。
- 入力検証：ID は32桁16進のみ、バックアップ名は固定パターンのみ受け付け、パスとして利用者の入力を使わない（設定画面のフォルダ指定を除く）。静的ファイルは拡張子の許可リストとパス正規化。画像は JPEG の構造を検証し、EXIF/GPS/XMP/コメントを除去（画面側でも再エンコードで除去）。
- 変更系の処理は独自ヘッダー必須（画面以外からの呼び出しを拒否）。
- ログ：処理名・ID・件数・利用者ID・処理時間のみ。検索語、名刺内容、連絡先は出力しない（テストで確認）。
- ブラウザ領域への保存：名刺データ・画像を localStorage / IndexedDB / キャッシュに保存しない。
- **アクセス制御は共有フォルダの権限に依存する**（アプリを使わなくてもファイルは読める）。そのため権限を利用者グループに絞ることが前提。

## 5. 取り込み用フォルダ・PDF

- 各利用者や複合機が共有フォルダ（取り込み用フォルダ）に画像・PDF を置くと、「未整理」に一覧表示する。自動では名刺として確定しない。
- 対象：jpg/jpeg/png/webp/heic/heif/pdf、30MB 以下、更新から10秒以上経過したもの（書き込み途中を避ける）。
- PDF：埋め込まれた JPEG（`/DCTDecode`、`[/FlateDecode /DCTDecode]`）を外部ライブラリなしで取り出す（`src/server/pdf.ts`）。取り込み用フォルダの PDF は `<元の名前>-p01.jpg`… に分割して元の PDF を取り込み済みへ移す（固定の名前で既存なら書かないので重複しない）。暗号化 PDF・JPEG 以外の画像の PDF は「取り出せない PDF」と表示する。
- 登録：PC間の `inbox` ロックの中で「元ファイルが残っている」ことを確かめてから名刺を保存し、保存が確定した後に元ファイルを取り込み済みへ移す（コピー → サイズ確認 → 元を削除）。他のPCが先に取り込んでいれば 409。

## 6. OCR

- Tesseract.js（WebAssembly）をアプリに同梱し、画面内で実行。エンジン約3MB、日本語・英語の学習データ（`best_int`）約5MB。外部からの取得は無効。
- 活字の横書き名刺は、会社名・住所・電話・メールなどを概ね拾える（架空の名刺で7項目を候補化、約1.3秒）。縦書き・デザイン性の高い名刺・小さい文字は誤りが多い。結果は入力候補として表示し、本人が確認・修正して反映する。保存は手動。

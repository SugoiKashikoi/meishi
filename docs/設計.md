# 設計メモ

## 1. 保存方式：共有フォルダ上の SQLite を採用しない理由

要件は「稼働中のデータそのものを社内共有フォルダに置く」ことです。最初に SQLite を検討しましたが、SQLite 公式資料は次の趣旨を述べています（下記 URL。**この開発環境からは sqlite.org に接続できず本文を再取得できなかったため、導入前に社内で原文を確認してください**）。

- <https://www.sqlite.org/useovernet.html>（SQLite Over a Network, Caveats and Considerations）
  ネットワークファイルシステムのファイルロックや書き込み順序・同期（fsync）の実装は不完全なことがあり、データベース破損の原因になり得る。クライアント／サーバー型の DB を使うか、DB はアプリサーバーのローカルディスクに置くことが推奨されている。
- <https://www.sqlite.org/wal.html>
  WAL モードは共有メモリを使うため、ネットワークファイルシステム上では動作しない（全プロセスが同一ホストにある必要がある）。
- <https://www.sqlite.org/howtocorrupt.html>
  ロック実装が壊れている／欠けているファイルシステム、同期が正しく行われないストレージが破損原因として挙げられている。

「アプリサーバー1台だけがアクセスするなら安全」とは言い切れず（ロック以外に、SMB のキャッシュ・通信断時の部分書き込み・ジャーナルとの整合が問題になる）、また要件上「ローカル DB ＋ 共有フォルダにはバックアップだけ」へ勝手に変更することもできません。そこで **単一のアプリサーバーが管理する、ファイル単位でアトミックに更新するストア** を共有フォルダ上に実装しました。

## 2. ファイルストアの構造

```
<dataDir>\
  .meishi-store        目印（init-store で作成。無ければ一切書き込まない）
  .lock                稼働中サーバーの識別子とハートビート（30秒ごと更新）
  cards\<id>.json      名刺1件 = 1ファイル（version 付き）
  images\<id>.jpg      画像（不変。差し替え時は新しい ID）
  trash\<id>-<時刻>.json  削除した名刺
  tmp\                 書き込み確認・復元アップロードの一時領域
<backupDir>\meishi-YYYYMMDD-HHMMSS-<auto|manual|pre-restore>.tar
```

### 整合性の仕組み

| 脅威 | 対策 |
|---|---|
| 書き込み途中の異常終了・通信断 | 同じフォルダに一時ファイルを書いて `fsync` → `rename` で置き換え → 読み戻して内容一致を確認。旧版か新版のどちらかが必ず残る。起動時に一時ファイルを掃除 |
| 名刺と画像の不整合 | 画像を先に保存し、名刺保存時に参照画像の存在を確認。画像は不変なので「名刺が無い画像」を参照する状態を作らない。参照されない画像は24時間後に掃除 |
| 同時保存（同一サーバー内） | 書き込みはプロセス内で直列化 |
| 複数端末の編集の重なり | `version` による楽観的排他。古い版からの保存は 409 で拒否し、画面に差分を表示（上書きするかは本人が選ぶ） |
| アプリの二重起動（別PCを含む） | `.lock` で拒否。異常終了時は2分経過、または同一PCで前回プロセスの終了を確認できれば引き継ぐ。稼働中に他者にロックを取られたら書き込みを停止 |
| 共有フォルダ切断 | 書き込み前に目印を確認。失敗時は 503 と明確なメッセージを返し、別の場所へは保存しない。切断中は一覧をメモリ上の最終状態で表示し、画面に「保存できません」と表示。30秒ごとの確認で再接続したらディスクから再読み込み |
| 読み込めない名刺ファイル | 削除せず `*.invalid-時刻` に退避してログに記録 |
| バックアップの整合 | 名刺はロック中にメモリから一括スナップショット、参照画像は掃除対象から除外（ピン留め）して書き出し。`manifest.json` に全ファイルの SHA-256。書き出し後に検証してから正式名に rename |
| 復元の途中失敗 | 検証 → 現データを `pre-restore` バックアップへ退避 → staging に展開 → `restore-in-progress.json` を書いてから `cards`/`images` を入れ替え。途中で止まった場合は次回起動時に入れ替えを完了 |

読み込みはメモリ上の索引（起動時に全件読み込み）で行います。利用者1人・数千〜1万件程度を想定しています。

### SMB 運用上の注意（社内環境で要確認）

- Windows ファイルサーバー／一般的な NAS（Samba）では、同一フォルダ内の置き換え rename はアトミックに扱われますが、NAS の機種・設定（キャッシュ、ウイルス対策のリアルタイム検査）によっては一時的に rename が失敗することがあります。その場合は保存失敗として表示されるので、もう一度保存してください。
- 共有フォルダのスナップショット機能（ボリュームシャドウコピー等）がある場合は併用を推奨します。

## 3. セキュリティ

- 認証：利用者ごとのログインIDとパスワード（scrypt でハッシュ化、サーバーのローカル `config\users.json`。旧形式の `auth.json` は管理者 `admin` として読み込み）。利用者の削除・パスワード変更は稼働中のサーバーにも即時反映し、該当するセッションを無効化。セッショントークンは乱数32バイトで、サーバー側はハッシュのみ保存。Cookie は HttpOnly・SameSite=Strict（HTTPS 時は Secure と `__Host-` 接頭辞）。
- ログイン試行制限：同一IP・同一IDそれぞれ5回失敗するとロック（5分から段階的に延長）、全体で15分30回まで。存在しないIDでも同じ計算を行い応答時間を揃える。
- 権限：全員が全名刺を閲覧・登録・編集・削除（ゴミ箱へ移動）できる共有モデル。名刺に `createdBy`/`updatedBy` を記録。バックアップ・復元・CSV出力は管理者のみ（サーバー側で 403）。
- 認可：`/api/*` はログイン・セッション確認以外すべて認証必須。画像も `/api/images/<id>` 経由で認証後のみ配信（`Cache-Control: private, no-store`）。画像フォルダは静的公開しない。
- CSRF：変更系 API は独自ヘッダー `X-Meishi-Request` 必須＋ Origin 一致確認＋ SameSite=Strict。
- 入力検証：ID は32桁16進のみ、バックアップ名は固定パターンのみ受け付け、パスとして利用者入力を使わない。静的ファイルは拡張子の許可リストとパス正規化。画像は JPEG のみ・サイズ上限・構造検証、EXIF/GPS/XMP/コメントを除去（クライアントでも再エンコードで除去）。
- CSP：`default-src 'self'`（外部への接続・読み込みをブラウザ側でも禁止）。`wasm-unsafe-eval` は OCR の WebAssembly のためだけに許可。
- ログ：メソッド・パス（ID は `:id` に置換）・ステータス・処理時間のみ。クエリ文字列（検索語）、名刺内容、パスワードは出力しない（テストで確認）。
- ブラウザ保存：名刺データ・画像を localStorage / IndexedDB / Service Worker キャッシュに保存しない。入力中の内容は画面のメモリ上にだけ保持し、離脱時は確認を出す。

## 4. 取り込み用フォルダ

- 各利用者・複合機が共有フォルダ（`inboxDir`）に名刺画像を置き、アプリは一覧時にフォルダを読み取って「未整理」として表示する（定期的な自動登録はしない）。
- 対象：拡張子 jpg/jpeg/png/webp/heic/heif、30MB 以下、更新から10秒以上経過したファイル（書き込み途中を避ける）。ID はファイル名・サイズ・更新日時のハッシュで発行し、API はこの ID だけを受け付ける。
- 登録の流れ：ブラウザが元画像を取得 → 縮小・回転・メタデータ除去して JPEG で通常どおりアップロード → 名刺保存時に `fromInbox` を指定 → **名刺の保存が確定した後**に元画像を `inbox-done` へ移動（コピー→サイズ確認→元を削除。別の共有でも動く）。移動に失敗しても名刺は保存済みとして扱い、画面で警告する。
- 二重登録防止：作業中の目印（30分）を表示し、既に移動済みの画像を指定した保存は 409 で拒否。
- 取り込み済み画像は `inboxRetentionDays` 経過後に削除。名刺として保存された画像は別途 `images` に保存されている。

### PDF の取り込み

- iPhone「メモ」の書類スキャンなどのスキャン PDF は、各ページを JPEG（`/DCTDecode`）で埋め込んでいる。外部ライブラリを使わず、`src/server/pdf.ts` で画像ストリームを取り出す（ページの描画はしない）。
- 対応：`/DCTDecode`、`[/FlateDecode /DCTDecode]`、`/Length` の直接値・間接参照。短辺100px未満の画像（サムネイル等）は除外し、取り出した画像も JPEG 構造検証とメタデータ除去を行う。
- 非対応：JPEG 以外で圧縮された画像（JBIG2・JPX・Flate のみ等）、暗号化 PDF、文字だけの PDF。明確なエラーを返し、取り込み用フォルダでは「取り出せない PDF」として表示する（破棄できる）。
- 取り込み用フォルダの PDF は `<元の名前>-p01.jpg`… に分割して同じフォルダに置き、元の PDF を取り込み済みへ移動。分割名は固定で既存なら書かないため、途中で止まって再実行しても重複しない。
- 登録画面で選んだ PDF は、画像を取り出して返すだけでサーバーに保存しない（1ページ目＝表、2ページ目＝裏）。

## 5. OCR の評価

| 方式 | 判断 |
|---|---|
| Tesseract.js（端末内、WebAssembly） | **採用（任意機能）**。無料・オフライン。エンジン（約3MB）と日本語・英語の学習データ（`best_int` 版、計約5MB）をアプリに同梱し社内サーバーから配信。外部 CDN からの取得を無効化（`workerBlobURL:false`、`cacheMethod:'none'`、ローカルパス指定） |
| 社内サーバーでの OCR（Tesseract 本体・PaddleOCR 等） | 精度向上の余地はあるが、Windows への追加ソフト導入・Python 環境などの負担が大きい。初期版は見送り |
| 外部 OCR / 生成AI API | 要件により不可 |

- 精度：活字の横書き名刺は、会社名・住所・電話・メールなどを概ね拾えます（開発環境の架空名刺で6項目を候補化、約1.3秒）。縦書き・デザイン性の高い名刺・小さい文字・手書きは誤りが多くなります。そのため結果は**入力候補**としてのみ表示し、本人がチェック・修正して反映、保存は手動です。
- 処理時間：iPhone 実機は未計測。初回は約8MBの読み込みが発生し、1枚あたり数秒〜数十秒を見込みます。重い場合は手入力で全機能を利用できます。
- OCR ファイルが無い（`public/vendor/ocr` を配置しない）場合は「文字を読み取る」ボタンが表示されないだけで、他の機能は動作します。
